**Status:** Frozen Initial Architecture & Data Contracts  
**Version:** 1.0.0-draft  
**Target Protocols:** HTTP/1.1 REST over JSON  

---

## 1. Domain Enums (Strictly Governed)

### 1.1 Permitted Outcome Enums
The deterministic rules engine is the sole authority for assigning outcomes. There are exactly **five (5)** permitted outcome values:

| Outcome Enum | Definition / Semantic Meaning |
|--------------|-------------------------------|
| `DISCREPANCY_CONFIRMED` | Irrefutable evidence that money moved inappropriately or state diverged (e.g., sender debited, receiver never credited, and no reversal executed within SLA). |
| `LIKELY_ROOT_CAUSE` | Clear evidence attributing failure to a specific leg (e.g., switch timed out during handoff to receiving bank, but switch journal confirms debit occurred). |
| `INSUFFICIENT_EVIDENCE` | Critical logs or evidence packets from one or more institutions are absent, precluding a conclusive finding without assuming unrecorded events. |
| `CONFLICTING_EVIDENCE` | Irreconcilable contradictory claims between institutions (e.g., switch asserts receiving bank returned SUCCESS, but receiving bank core logs assert transaction rejected). |
| `NO_DISCREPANCY_FOUND` | All participating institution records reconcile completely; debits, credits, and fees match expected terminal state. |

> **Contract Rule:** No component or LLM may introduce, map to, or invent additional outcome enums.

### 1.2 Permitted Finding Strength Labels
Finding certainty is communicated via **qualitative strength labels**. Numerical confidence percentages (e.g., "94.2% confidence") are **strictly prohibited** because they imply probabilistic ML scoring rather than deterministic evidence audits.

| Strength Label | Definition / Governance Rule |
|----------------|------------------------------|
| `HIGH` | Complete evidence chain present with valid correlation identifiers across all legs and zero critical data-quality flags. |
| `MODERATE` | Clear evidence chain, but minor caveats exist (e.g., acceptable clock skew, minor metadata gap) OR capped from HIGH due to data-quality flags. |
| `LOW` | Weak correlation or notable gaps in intermediate logs, though a directional pattern is identifiable. |
| `INSUFFICIENT` | Evidence is inadequate to support a substantive finding; the default and mandatory strength for an `INSUFFICIENT_EVIDENCE` outcome **except** where a documented exception below applies. |

**Documented strength exception (rule H).** The strength label describes *evidential certainty*, while the outcome label describes *the transaction conclusion*. These are normally aligned (`INSUFFICIENT_EVIDENCE` ⇒ `INSUFFICIENT`), with a single deliberate exception. Under **rule H (unlinked similar evidence)**, the transaction conclusion is correctly `INSUFFICIENT_EVIDENCE` (records cannot be authoritatively linked), but the co-located amount and currency constitute a weak *directional* pattern of a possible linkage. Because §1.2 defines `LOW` as "a directional pattern is identifiable", rule H emits `LOW`. This is the only outcome/strength pairing permitted to differ from the default; rules E2, G and I remain `INSUFFICIENT_EVIDENCE` / `INSUFFICIENT`. See §5.2 (rule H) and §5.4.

### 2.2 Nested Structure Specifications

#### `timeline` (Array of `TimelineEvent`)
- `event_id` (UUID, required): Unique identifier for the canonical normalized event.
- `timestamp` (ISO 8601 string with timezone, required): Canonical event timestamp.
- `party` (Enum string, required): `ORIGINATING_BANK`, `SWITCH`, `RECEIVING_BANK`, `MERCHANT`.
- `action` (Enum string, required): `DEBIT`, `CREDIT`, `SWITCH_IN`, `SWITCH_OUT`, `ACK`, `REVERSAL_ATTEMPT`, `TIMEOUT`.
- `status` (Enum string, required): `SUCCESS`, `PENDING`, `FAILED`, `TIMEOUT`.
- `amount_minor_units` (Integer, required): Amount in integer minor units (e.g., 8500000 kobo).
- `currency` (String, required): 3-letter currency code (e.g. `NGN`).
- `reference` (String, optional): Institution-scoped transaction reference.
- `session_id` (String, optional): Cross-institution correlation session identifier.
- `rrn` (String, optional): Retrieval Reference Number.
- `raw_record_id` (UUID, required): Lineage pointer to immutable raw source record.
- `data_quality_notes` (String, optional): Specific data caveat attached to this event.

#### `missing_evidence` (Array of `MissingEvidenceItem`)
- `expected_party` (Enum string, required): The party from whom a record was expected.
- `expected_action` (Enum string, required): The action expected (e.g., `CREDIT`, `ACK`).
- `window_start` (ISO 8601 string, required): Start of expected arrival window.
- `window_end` (ISO 8601 string, required): End of expected arrival window.
- `reason` (String, required): Explanation of why this piece of evidence was expected.
- `evidence_type` (String, optional): High-level category of the missing evidence (e.g. `REVERSAL_RECORD`, `SETTLEMENT_CREDIT`).
- `description` (String, optional): Human-readable description of the absent record.
- `impact` (String, optional): Deterministic impact of the absence on the finding.
- `recommended_request` (String, optional): Actionable acquisition request to the responsible institution.

#### `data_quality_flags` (Array of `DataQualityFlagItem`)
- `flag_code` (String, required): Machine-readable flag code (e.g. `CLOCK_SKEW_EXCEEDED`, `CLOCK_SKEW_AMBIGUOUS_ORDERING`, `AMBIGUOUS_CORRELATION`, `UNRESOLVED_RRN_COLLISION`, `MISSING_SESSION_ID`).
- `severity` (Enum string, required): `LOW`, `MEDIUM`, `CRITICAL`. (Note: `CRITICAL` automatically caps finding strength at `MODERATE`).
- `description` (String, required): Human-readable description of the anomaly.
- `affected_event_ids` (Array of UUIDs, required): IDs of impacted events.
- `impact` (String, required): Concrete effect on analysis determination.

#### `counterfactuals` (Array of `CounterfactualItem`)
- `scenario` (String, required): Description of hypothetical alternate evidence.
- `condition` (String, required): Concrete condition that would alter the finding.
- `outcome_if_condition_met` (Enum string, required): The resulting outcome enum if the condition were true.
- `explanation` (String, required): Logical explanation of the counterfactual outcome.

#### Justification & Traceability Fields (Part 4)
These fields are additive to the 10 required contract fields and default to empty when not applicable.
- `outcome_reason` (String): Deterministic, non-probabilistic justification for the selected outcome.
- `strength_reason` (String): Deterministic justification for the selected qualitative strength, including any capping applied.
- `scope_examined` (String): Summary of the evidence scope evaluated (canonical event count, correlation group breakdown).
- `supporting_evidence` (Array of UUIDs): Event IDs affirming the selected outcome.
- `contradicting_evidence` (Array of UUIDs): Event IDs contradicting the selected outcome.
- `alternative_explanations` (Array of Strings): Alternative hypotheses not excluded by available evidence.
- `recommended_next_evidence` (Array of `RecommendedEvidenceItem`): Prioritised evidence acquisition recommendations.

#### `recommended_next_evidence` (Array of `RecommendedEvidenceItem`)
- `evidence_type` (String, required): Category of evidence requested (e.g. `REVERSAL_RECORD`, `SETTLEMENT_CREDIT`, `SOURCE_FILE_REUPLOAD`).
- `expected_party` (Enum string, optional): Institution expected to supply the evidence.
- `rationale` (String, required): Why this evidence would materially change the finding.
- `related_event_ids` (Array of UUIDs): Existing event IDs the request relates to.

### 3.5 `POST /api/v1/cases/{id}/evidence`
Ingests, validates, and normalizes synthetic institution evidence files (CSV or JSONL).

**Path Parameter**: `id` (UUID)  
**Request Format**: `multipart/form-data` containing:
- `file` (File, required): CSV or JSONL file
- `institution_source` (Enum string, required): `ORIGINATING_BANK`, `SWITCH`, `RECEIVING_BANK`, `MERCHANT`
- `file_type` (String, optional): `CSV` or `JSONL` (inferred from extension if omitted)

**Upload Limits**:
- Max file size: 5 MB (5,242,880 bytes).
- Max records per batch: 2,000 rows.

**Source-Specific Required & Optional Fields**:
- `ORIGINATING_BANK`:
  - Required: `timestamp` (ISO 8601 with offset), `reference`, `amount` (integer minor units), `currency`, `status`
  - Optional: `action` (default `DEBIT`), `session_id`, `rrn`, `channel`, `account_number`, `narration`
- `SWITCH`:
  - Required: `timestamp`, `session_id`, `action`, `status`, `amount`, `currency`
  - Optional: `rrn`, `reference`, `source_institution`, `destination_institution`, `response_code`
- `RECEIVING_BANK`:
  - Required: `timestamp`, `reference`, `amount`, `currency`, `status`
  - Optional: `action` (default `CREDIT`), `session_id`, `rrn`, `beneficiary_account`, `narration`
- `MERCHANT`:
  - Required: `timestamp`, `order_id`, `reference`, `amount`, `currency`, `status`
  - Optional: `action` (default `ACK`), `session_id`, `rrn`, `customer_id`

**Response `201 Created`**:
```json
{
  "source_file_id": "5a415a78-2d33-4f3b-871d-1eb95627f098",
  "case_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "filename": "synthetic_switch_logs_20261014.csv",
  "records_ingested": 142,
  "sha256_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "status": "INGESTED"
}
```

**Client Error Responses**:
- `400 Bad Request`: Validation failure (malformed JSONL, invalid CSV headers, missing fields, floating-point amounts, timezone-naive timestamp, unsupported currency).
  ```json
  {
    "error": "Floating-point representation '85000.50' is prohibited. Monetary values must be integer minor units (e.g., 8500000 kobo).",
    "details": {
      "row_index": 2,
      "field": "amount"
    }
  }
  ```
- `404 Not Found`: Target case ID does not exist.
  ```json
  {
    "error": "Case with ID '3fa85f64-5717-4562-b3fc-2c963f66afa6' was not found.",
    "details": {
      "case_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6"
    }
  }
  ```
- `409 Conflict`: Duplicate evidence file uploaded for this case (matching SHA-256 hash).
  ```json
  {
    "error": "Duplicate evidence detected. File with SHA-256 hash 'e3b0c442...' was already ingested for this case.",
    "details": {
      "case_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
      "sha256_hash": "e3b0c442...",
      "existing_source_file_id": "5a415a78-2d33-4f3b-871d-1eb95627f098"
    }
  }
  ```
- `413 Payload Too Large`: Uploaded file exceeds 5MB ceiling.
  ```json
  {
    "error": "Uploaded file size (6144000 bytes) exceeds maximum allowable limit of 5242880 bytes.",
    "details": {
      "size_bytes": 6144000,
      "max_bytes": 5242880

  }
  ```

### 3.8 `POST /api/v1/cases/{id}/review`
Records a separate human decision; it does not alter TRACE's deterministic finding.

**Request body**: `reviewer_display_name` (unverified metadata), `decision`
(`ACCEPT_FINDING`, `DISPUTE_FINDING`, or `REQUEST_MORE_EVIDENCE`), and a non-blank
`rationale`; optional `notes` and `requested_additional_evidence` are supported.

The server recalculates the authoritative finding and persists a compact JSON snapshot with a
SHA-256 finding reference alongside the review. This is a historical snapshot at review time, not
a claim of tamper-proof storage or authenticated authorship.

## 4. Deterministic Correlation Contract (Part 3)

### 4.1 `GET /api/v1/cases/{id}/correlation`

Deterministically identifies which normalized events for a case can be reliably linked, which are candidate matches, and which are ambiguous or unmatched. Correlation is **read-only** and is computed on demand from persisted canonical events.

**Path Parameter**: `id` (UUID)

> **Correlation does not decide transaction outcomes.** It never infers success, failure, reversal, or discrepancy, and does not use the five outcome enums or four strength labels. It only classifies linkage certainty.

**Response `200 OK`**:
```json
{
  "case_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "algorithm_version": "2026.1.0-corr",
  "computed_at": "2026-10-15T00:05:10.000+01:00",
  "total_events": 2,
  "groups": [
    {
      "group_id": "b6f1c8de-6a1e-5c21-9b0c-6a2f4b1d9e77",
      "status": "CONFIRMED",

      "reason_code": "STRONG_SESSION_AND_RRN_CONSISTENT",
```

### 4.2 Correlation Status States

| Status | Meaning | Source Events Merged? |
|--------|---------|-----------------------|
| `CONFIRMED` | Linked by mutually consistent **global** identifiers (`session_id`/`rrn`), or by a verified cross-source shared reference. | Logically linked; source rows unchanged |
| `CANDIDATE` | Partial match (reused institution-local reference, or equal amount + currency within ±5s). Requires human review. | **No** — explicitly unmerged |
| `AMBIGUOUS` | Material identifier conflict (conflicting session_id/RRN, conflicting currency, transitive identifier conflict). | **No** |
| `UNMATCHED` | Insufficient identifiers or unresolved conflict. | **No** |

### 4.3 Method & Reason Codes

`method` ∈ {`SESSION_AND_RRN_MATCH`, `SESSION_ID_MATCH`, `RRN_MATCH`, `INSTITUTION_SCOPED_REFERENCE`, `TEMPORAL_AMOUNT_PROXIMITY`, `PARTIAL_REFERENCE_HEURISTIC`, `NONE`}.

`identifier_scope` ∈ {`GLOBAL_INTERBANK`, `INSTITUTION_LOCAL`, `NONE`}.

`reason_code` ∈ {`STRONG_SESSION_AND_RRN_CONSISTENT`, `STRONG_SESSION_ID_CONSISTENT`, `STRONG_RRN_CONSISTENT`, `SECONDARY_INSTITUTION_REFERENCE_VERIFIED`, `AMBIGUOUS_IDENTIFIER_CONFLICT`, `AMBIGUOUS_MULTIPLE_CANDIDATE_COLLISION`, `CANDIDATE_TEMPORAL_AMOUNT_PROXIMITY`, `CANDIDATE_PARTIAL_REFERENCE_ONLY`, `INSUFFICIENT_IDENTIFIERS`, `CURRENCY_MISMATCH`, `TIMESTAMP_OUT_OF_TOLERANCE`, `CROSS_CASE_BOUNDARY_VIOLATION`}.

### 4.4 Contract Guarantees

- **Deterministic & versioned**: identical normalized events + same `algorithm_version` ⇒ identical `groups`/`summary`; all lists sorted; output independent of database retrieval order.
- **Pure**: source `events` and `raw_records` are never mutated; no correlation tables are persisted by this design, so re-runs cannot create duplicate groups.
- **Provenance preserved**: each member exposes `event_id`, `raw_record_id`, party, timestamp, and identifiers.
- **Uncertainty preserved**: `contradictions`, `temporal_ordering_ambiguous`, and `duplicate_identity_event_ids` remain visible and are never auto-resolved.
- **Single-case scoped**: cross-case correlation is rejected (`CrossCaseCorrelationError`, HTTP 400).

## 5. Deterministic Rules Engine Contract (Part 4)

### 5.1 Versioning & Purity

- **Rule version**: `2026.1.0-rules`. The engine stamps this version on every response (`rule_version`); the `rule_version` request override is intentionally not honored so a caller can never mislabel a finding.
- **Pure & deterministic**: `evaluate_case(case, events)` is a pure function. Identical canonical inputs yield byte-for-byte identical `AnalysisResponse` values, including all sorted evidence-ID lists. It never mutates events and never writes to the database.
- **Linkage-dependent rules are gated on Part 3 `CONFIRMED` groups only.** Amount/time proximity (candidate or ambiguous) can never confirm a discrepancy or a clean settlement.
- **Duplicate collapse**: records sharing an identical evidence signature are collapsed to a single canonical leg; the duplicate is surfaced via a `DUPLICATE_EVIDENCE` (LOW) flag and never treated as a second payment.

### 5.2 Rule Precedence

Rules are evaluated in strict precedence order; the first matching rule wins.

**Leg model.** Each core action belongs to exactly one payment leg: `DEBIT` → *ORIGINATION*, `SWITCH_OUT` → *OUTBOUND_TRANSIT*, `SWITCH_IN` and `CREDIT` → *INBOUND_SETTLEMENT*. Rules A and D/D2 depend on this distinction: opposing terminal statuses only contradict when they occur on the **same leg**; opposing terminal statuses on **different legs** describe a cross-stage sequence (a downstream failure), which is consistent, not contradictory.

| # | Rule | Condition | Outcome / Strength |
|---|------|-----------|--------------------|
| A | Same-leg terminal contradiction | A `CONFIRMED` group contains, **on the same leg**, both `SUCCESS` and `FAILED` terminal statuses (e.g. `SWITCH_IN` success vs `CREDIT` failed — both inbound/settlement) | `CONFLICTING_EVIDENCE` / `LOW` |
| B | Linked amount mismatch | A `CONFIRMED` group links a successful debit and credit with divergent amounts | `DISCREPANCY_CONFIRMED` / `HIGH` |
| C | Multiple unreversed debits | ≥2 **independently distinguishable** successful sender debits (not unresolved by a CANDIDATE/AMBIGUOUS correlation group), with no reversal or refund | `DISCREPANCY_CONFIRMED` / `MODERATE` |
| D | Downstream timeout | Successful upstream leg(s) (`DEBIT`/`SWITCH_OUT`) + timeout leg(s) and no successful credit | `LIKELY_ROOT_CAUSE` / `MODERATE` |
| D2 | Downstream failure (explicit) | Successful upstream leg(s) + a `FAILED` receiving-bank credit and no successful credit; the failed credit is affirmative failure evidence (preserved in `supporting_evidence`) | `LIKELY_ROOT_CAUSE` / `MODERATE` |
| D3 | Reversal vs downstream value | Successful debit matched by a successful system reversal **and** a successful credit/merchant payment; funds cannot be both returned and delivered | `CONFLICTING_EVIDENCE` / `LOW` |
| E | System reversal | Successful debit(s) matched by a successful system reversal (no independent downstream value movement) | `NO_DISCREPANCY_FOUND` / `MODERATE` |
| E2 | Unverified merchant refund | Merchant refund/ack present, no system reversal and no receiving-bank credit | `INSUFFICIENT_EVIDENCE` / `INSUFFICIENT` |
| F | Clean settlement | A `CONFIRMED` group links a successful debit to a successful receiving-bank credit with consistent amounts and no failed core legs | `NO_DISCREPANCY_FOUND` / `HIGH` |
| G | Downstream success, no settlement | Downstream success leg(s) exist but no receiving-bank credit | `INSUFFICIENT_EVIDENCE` / `INSUFFICIENT` |
| H | Unlinked similar evidence | ≥2 events share amount + currency but are not authoritatively linked | `INSUFFICIENT_EVIDENCE` / `LOW` *(documented exception, §1.2)* |
| I | Fallback | No rule matched | `INSUFFICIENT_EVIDENCE` / `INSUFFICIENT` |

### 5.3 Strength Capping

- `CRITICAL` and `MEDIUM` data-quality flags (e.g. `IDENTIFIER_CONFLICT`, `CURRENCY_CONFLICT`, `CLOCK_SKEW_AMBIGUOUS_ORDERING`, `EVENT_ORDER_ANOMALY`) cap an otherwise-strong finding at `MODERATE`.
- `LOW` severity flags (e.g. `DUPLICATE_EVIDENCE`) never cap strength and are surfaced for audit only.
- The cap only ever lowers strength; it never raises it.

### 5.4 Contract Guarantees

- **No probabilities**: strength is a qualitative label only; no percentages or numeric confidence are emitted.
- **Absence is not proof**: missing legs degrade to `INSUFFICIENT_EVIDENCE` and are enumerated in `missing_evidence` / `recommended_next_evidence`, never assumed to have failed.
- **Strength invariant (§1.2)**: every rule that returns `INSUFFICIENT_EVIDENCE` emits `INSUFFICIENT` strength (rules E2, G, I) **except** rule H, the single documented exception, which emits `LOW` to convey a weak directional (possible-linkage) pattern; `LOW` is never used for any other insufficient finding.
- **Cross-stage sequences are not contradictions**: a `SUCCESS` on one payment leg and a `FAILED` status on a *later* leg (e.g. sender `DEBIT` success + receiving-bank `CREDIT` failed) are treated as a consistent cross-stage failure (rules D/D2), not as conflicting evidence; the failed leg is preserved in `supporting_evidence`.
- **Contradictions are surfaced**: whenever a finding would otherwise ignore genuinely incompatible evidence (e.g. same-leg opposing terminal statuses, or a successful reversal/credit alongside a downstream payment), those events are enumerated in `contradicting_evidence` and never silently discarded.
- **Disjoint evidence sets**: `supporting_evidence` and `contradicting_evidence` never overlap; every referenced ID belongs to a canonical (post-deduplication) event.
- **Traceability**: every finding exposes `supporting_evidence`, `contradicting_evidence`, `alternative_explanations`, and `data_quality_flags`.
- **Read-only**: no money movement, transfers, refunds, or reversals are ever initiated.
